## Prisma 8 (not the classic Prisma you may know)

There is no `schema.prisma`, `prisma-client-js`, `prisma generate`, `migrate dev` or `directUrl`. Authoritative docs ship in `node_modules/@prisma/orm-postgres/skills/prisma-8/references/` (`contract.md`, `migrations.md`, `runtime.md`, `supabase.md`); `prisma-8.md` at the root is a short overview.

- **`prisma/contract.prisma`** is the source of truth for models. `contract.json` and `contract.d.ts` are generated by `pnpm contract:emit` and must be committed; re-run it after every contract edit or the typed client goes stale.
- **`prisma.config.ts`** (CLI) and **`prisma/db.ts`** (runtime `postgres()` client) both read only `DATABASE_URL`. Query with `db.orm.public.<Model>` (note the `public` namespace). Use it only on the server (Server Actions, Route Handlers, Server Components).
- **Shared columns** use a mixin, not a model: `model mixin DefaultCols { ... }` included with `+DefaultCols`. A mixin cannot be overridden by a model that declares the same field, and `@@rls` cannot be assumed to work inside a mixin, so put it on each model.
- Date fields use `TimestamptzString` / `temporal.updatedAtString()` (values are strings, not `Date`).

### Supabase connection

- `DATABASE_URL` must be the **session pooler** (port 5432, user `postgres.<project-ref>`, database name `postgres`) or the direct connection. Never the transaction pooler (6543). `DIRECT_URL` is unused.
- The app talks to Postgres directly as `postgres` (`BYPASSRLS`). Supabase's REST API is not used, so **every model needs `@@rls`** (enabled, no policies = deny-all for `anon`/`authenticated`); otherwise Supabase flags the table as unrestricted.

### Migrations workflow

Formal migrations are in use (do not use `db update`/`db init`; they advance the `db` ref past the migration graph and cause `MIGRATION.HASH_NOT_IN_GRAPH`):

```bash
pnpm contract:emit
pnpm prisma migration plan --name <change>   # writes migrations/app/<timestamp>_<name>/; review the DDL preview
pnpm prisma db migrate --advance-ref db      # apply; --advance-ref keeps migrations/app/refs/db.json current
pnpm prisma db verify                        # contract vs live DB
pnpm prisma migration status
```

- Without `--advance-ref db`, the next `migration plan` fails with `MIGRATION.PLAN_ORIGIN_UNKNOWN`; the fix is `--from <hash>` or `pnpm prisma migration ref set db <hash>`.
- Commit `migrations/` entirely (packages, `snapshots/`, `refs/db.json`) together with the regenerated `contract.*`.
- Prisma's own state lives in the `prisma_contract` schema of the database; do not touch it by hand.

## Architecture

Each feature follows the same layering; copy the existing ones (`leads`, `pipelines`, `templates`) when adding another.

- `app/<feature>/{types,schemas}.ts` hold the types and the zod schemas shared by client and server. `_components/` and `_store/` (zustand) are the client side; `_components/Provider.tsx` copies the server-fetched `data` into the store.
- `app/api/<feature>/**/route.ts` validate the request with the schema and call a server action. Errors go through `errorResponse` / `handleDbError` from `lib/response.ts` (404 via the `notFound` message, FK violation 400, unique violation 409).
- `server/actions/<feature>/{get,post,patch,delete}.ts` are the `'use server'` actions that talk to `db`. A `'use server'` file may only export async functions, so shared constants (`LEAD_NOT_FOUND`, `TEMPLATE_NOT_FOUND`, ...) live in `server/queries/`.
- Pages are server components that `await connection()`, fetch with the action, and wrap the UI in `Provider`. Client code calls the API with `lib/api.ts` (`api`, `getApiErrorMessage`); `router.refresh()` after a mutation.
- Deletes are soft (`deletedAt`); every read filters `deletedAt: null`.
- Dialog + form + actions-dropdown pattern: see `pipelines/_components/PipelineActions.tsx`. Lists with row actions use `helper.display({ id: 'actions' })` in the TanStack table.
- **Security note — auth is pending.** No authentication exists yet: every API route and `'use server'` action is open (a `'use server'` function is a publicly callable endpoint). This matters most because of the Evolution API integration: anyone who can reach `POST /api/whatsapp/send` or the `sendTemplate` action can make the connected WhatsApp number send messages. The lead import and template image upload are open too. Add an auth method (e.g. Supabase Auth with a `proxy.ts` guarding `/api/*` and the pages, plus the same check inside each server action) before exposing the app beyond a private network.

## Supabase Storage

- `server/storage/index.ts` (`server-only`) wraps `@supabase/supabase-js` with the secret key: `uploadFile(bucket, file)` and `deleteFile(bucket, pathOrUrl)`. Object keys are `<uuid>.<ext>` with the extension taken from an allow-list of image MIME types, never from the client file name.
- The bucket is public; `Template.img` stores the public URL.
- Env: `SUPABASE_URL`, `SUPABASE_SECRET_KEY` (never `NEXT_PUBLIC_`), `SUPABASE_TEMPLATES_BUCKET` (defaults to `templates`).
- Template create/update take `multipart/form-data` (`name`, `message`, optional `image`, `removeImage=true` on PATCH). Actions upload first and delete the new file if the DB write fails; replacing or removing an image deletes the old object.

## Templates and rich text

- `Template.message` is HTML from the Tiptap editor (`components/RichTextEditor.tsx`: bold, italic, strike, bullet/ordered lists). It is sanitized on the server with `server/sanitize.ts` (allow-list, no attributes) before saving, and rendered with `components/RichTextContent.tsx`, which trusts already-sanitized HTML. Extend the allow-list there if new editor marks are added.

## Lead import

- `components/ImportLeadsDialog.tsx` (reusable, used in `/leads` and `/pipelines`) posts a `.xlsx`/`.csv` to `POST /api/leads/import`. The route parses with `server/parsers/leads.ts` (first sheet, columns `Contacto principal`, `Teléfono celular (contacto)`, `Captación (contacto)`) and calls `server/actions/leads/import.ts`, which skips existing/duplicate phones and returns `{ created, skipped[] }`.
- `xlsx` is installed from the SheetJS CDN tarball (npm's 0.18.5 has known vulnerabilities); keep it that way. CSV is decoded as UTF-8 before parsing, otherwise accents break.

## WhatsApp (Evolution API)

- `server/whatsapp/evolution.ts` (`server-only`) sends a template with simulated typing (`sendPresence` composing for a duration proportional to the message length, then `sendText` or `sendMedia`). Images go by URL first and fall back to multipart. Phones are normalized to digits, with country code `51` prepended to 9-digit numbers.
- `server/whatsapp/htmlToWhatsApp.ts` converts the template HTML with `turndown` to WhatsApp formatting.
- Entry points: `sendTemplate` action and `POST /api/whatsapp/send` (`{ phone, templateId }`). No UI uses them yet.
- Env: `EVOLUTION_API_PREFIX`, `EVOLUTION_API_INSTANCE_ID`, `EVOLUTION_API_KEY`. Never log raw axios errors (they contain the apikey header); use `describeError`.

## Workflows (lead movement)

- A `WorkflowPipeline` moves leads from `fromPipelineId` to `toPipelineId`. Exactly one of `whenResponse`, `whenNotResponse`, `whenSendMessage` is true; `waitingTime` is in **minutes**. When a pipeline has several matching workflows, the most recent (highest `id`) wins.
- `Lead` timestamps (all `timestamptz`): `lastContact` (last message we sent), `lastResponseAt` (last answer), `movedAt` (last pipeline change). The cron counts `whenNotResponse` from the later of `lastContact` and `movedAt`, so a lead cannot chain through several pipelines in one run.
- `server/workflows/moveLeads.ts` is the only place that moves leads. It updates with `WHERE pipelineId = from`, so repeated webhooks, overlapping cron runs or a manual drag never move a lead twice. These helpers are plain modules, not `'use server'` files, so they are not callable endpoints.
- **Webhook**: `POST /api/whatsapp/webhook[/...event]` (Evolution `messages.upsert`) -> `server/whatsapp/handleWebhookEvent.ts` -> `onIncomingMessage.ts`. It ignores own messages, statuses and groups, finds the lead by exact phone (`server/whatsapp/phone.ts`: international, `+international` or 9-digit local; never by suffix), sets `messageResponse = true` and `lastResponseAt`, and moves the lead right away when the `whenResponse` workflow has `waitingTime = 0`. The webhook has no authentication yet (same as the original project).
- **`@lid` linking**: users with a WhatsApp username arrive with `remoteJid = <n>@lid` and no phone. `sendTemplateMessage` stores the id Evolution returns (`response.key.id`) in `Lead.lastMessageId` (with `lastContact`). The `messages.update` ack (`fromMe`, `keyId`, `remoteJid` = `@lid`) is matched by `lastMessageId` and sets `Lead.lid` if it is still null. Incoming `messages.upsert` finds the lead by `lid` first, then by phone. `lastMessageId` is overwritten on each send; later acks (DELIVERY_ACK/READ) retry the link if the first one raced the DB write.
- **Cron**: `instrumentation.ts` -> `server/cron/startCronJobs.ts` starts one cron per module (`startWorkflowsCron.ts` -> `server/workflows/run.ts` `runWorkflows`, `startDiffusionsCron.ts` -> `runDiffusions`); workflows run with `node-cron` every minute (`* * * * *`; `CRON_WORKFLOWS_SCHEDULE` overrides it, `CRON_ENABLED=false` turns it off). It only works on a long-running Node server (Docker), not serverless. With several instances it is still safe because of the guarded update.
- `whenSendMessage` is applied right when a message is sent (`server/whatsapp/leadContact.ts`, called by `sendTextMessage`/`sendMediaMessage`); `whenResponse` is applied by the webhook. The workflows cron only evaluates `whenNotResponse`.

## Diffusions (sending)

- `server/diffusions/run.ts` (`runDiffusions`) is driven by its own cron in `server/cron/startDiffusionsCron.ts` (`CRON_DIFFUSIONS_SCHEDULE`, default every 15 s). State lives in the DB, so it survives restarts.
- One diffusion runs at a time (`active`/`sending`/`failed`); `pending` ones start in `id` order once `startAt` is null or due.
- Per tick: take the next `pending` `LeadInDiffusion` (claimed with a guarded update) -> diffusion `sending`, lead `sending` with a random template of the diffusion -> `sendTemplateMessage`. Sent: lead `sent`, diffusion `active` with `nextSendAt` = now + 3/5/8/10 min at random. Failed: lead `failed` with `error`, diffusion `failed`, and the next lead is tried immediately (no wait). No pending leads left: diffusion `completed` + `finishedAt`. Every lead records `templateId`, `sentAt` (also on failure) and `waited`; `Diffusion.processed/sent/failed` are synced after each lead.
- Cancelling sets `cancelled`; the runner stops at the next lead. A lead stuck in `sending` for 5 min is marked `failed` ("Envío interrumpido").
- **Dashboard (`/`)**: `app/_components/CurrentDiffusion.tsx` shows the running diffusion (or else the oldest pending one) and updates live through SSE (`GET /api/diffusions/stream`). `server/diffusions/events.ts` is an in-memory emitter on `globalThis`; the runner and the create/patch/delete actions call `publishDiffusionChange()` and the stream re-reads `getCurrentDiffusion()`. Single instance only. Cancel is allowed in every status except `completed`/`cancelled`; the runner's status writes are guarded (`updateRunning`) so a cancel is never overwritten.
